## OpenCypher Analysis & Roadmap Revision

After comprehensive OpenCypher specification research, the v0.2 plan was revised:

### Key Finding

**v0.2 is NOT "feature complete for full OpenCypher"** — It represents **~25% TCK compliance**, providing essential features for 80% of typical use cases.

### Compliance Trajectory

| Version | TCK Scenarios | Percentage | Description |
|---------|--------------|------------|-------------|
| v0.1.4 | 638/3,837 | 16.6% | Current release |
| v0.2.0 | ~950/3,837 | ~25% | Core Cypher Complete |
| v0.3.0 | ~1,500/3,837 | ~39% | Advanced Patterns |
| v1.0 | ~2,800/3,837 | ~73% | Full core OpenCypher |

### Changes to Original Plan

**Moved to v0.3:**
- the work item (Path expressions) - Too complex for v0.2, focus on breadth not depth

**Added to v0.2 (Quick Wins):**
- the work item (REMOVE clause) - 2h, high user value
- the work item (Arithmetic operators) - 2-3h, fundamental functionality
- the work item (COLLECT aggregation) - 3-4h, most requested aggregation
- the work item (String matching) - 2-3h, very common in queries
- the work item (NOT operator) - 1-2h, essential logical operator

**Rationale:**
- Better **breadth** (more diverse features) vs. depth (complex niche features)
- Focus on **high-impact, commonly-used** features
- **Honest positioning:** "Core Cypher-compatible" not "feature complete"
- Establish **multi-version roadmap** to true OpenCypher compliance

## Workflow: Issue → Branch → PR → Merge

### Starting Work

```bash
# Example: Starting work on UNWIND
git checkout main
git pull origin main
git checkout -b feature/20-unwind-clause

# Work on feature...
```

### Creating a PR

```bash
git push -u origin feature/20-unwind-clause

gh pr create \
  --title "feat: implement UNWIND clause for list iteration" \
  --body "Closes #<issue-number>

## Summary
[Feature summary here]

## Testing
[Test summary here]" \
  --label "enhancement,v0.2"
```

### Automatic Linking

Using `Closes #<issue-number>` or `Fixes #<issue-number>` in the PR description will:
- Automatically link the PR to the issue
- Close the issue when the PR is merged
- Update the milestone progress

## Key Decision: Honest Positioning

**Original claim:** "v0.2 - Feature complete for full OpenCypher"
**Revised positioning:** "v0.2 - Core Cypher-compatible for common graph operations"

After OpenCypher TCK analysis, v0.2 represents ~25% compliance (950/3,837 scenarios), not "full OpenCypher." The revised plan:
- **Provides better breadth** - 9 diverse features vs. 5 (with 1 very complex)
- **Sets honest expectations** - Clear about gaps and limitations
- **Establishes roadmap** - Multi-version path to 70-75% compliance (v1.0)
- **Builds trust** - Transparent about what GraphForge is and isn't

GraphForge is **not** competing with Neo4j as a production database. It's an **embedded, SQLite-like graph query engine** for Python data science workflows — and that's a valuable, unique position.
